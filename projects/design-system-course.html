Design System Course

A self-authored course for practicing how a design system actually gets built: starting from a deliberately inconsistent fictional provider portal, "Prescription Desk," and working through audit, tokens, accessibility foundations, component extraction, product patterns, theming, and documentation in order.

I make every design-system decision and write the design-system code. The coaching workflow explains tradeoffs, asks questions, reviews the result, and keeps a running record so the process stays evidence-based instead of vibes-based.

8 staged curriculum, Stage 0 (audit) through Stage 7 (documentation and maintenance)
4 reviewer roles: coach, architecture reviewer, accessibility reviewer, implementation reviewer
10 design-system decisions recorded so far, each with reasoning and alternatives considered
0 tokens or components shipped yet — still inside Stage 0, by design

A deliberately broken starting point

Prescription Desk is a small React and TypeScript app: a worklist, a request detail screen, and a new-request form, each with its own local stylesheet. The inconsistencies are intentional raw material, not oversights — three near-identical primary buttons with different colors, radii, padding, and disabled treatments; three different focus-ring colors; mismatched headings, status badges, and error styles.

Nothing gets "fixed" outside the course. Every inconsistency is first audited, classified, and traced to its source files and consumers before anything is extracted or tokenized.

A structured coaching workflow

Four role-based agents keep the process honest: a coach that runs the curriculum and asks before assuming, an architecture reviewer, an accessibility reviewer, and an implementation reviewer. A review pass applies all three reviewer roles in sequence rather than treating them as independent opinions.

Task guides cover auditing a screen, choosing tokens, migrating a consumer, reviewing a component API, and checking accessibility. Course state lives in four files — a roadmap, the active session, a decision log, and an inventory — so any session can resume from exactly where the last one left off.

Staged curriculum

Audit before tokens, tokens before components, components before patterns.

Each stage has to be earned by the one before it. Accessibility, documentation, and tests run through every stage rather than arriving at the end.

Stages 0–2

Audit repeated patterns and classify them by layer, then build reference tokens (one family first) and semantic aliases with a real use case before expanding.

Stages 3–5

Consistent focus, error, and feedback foundations; components extracted only after comparing real consumers; product patterns composed from the system, migrated one consumer at a time.

Stages 6–7

Themes as alternative mappings, tested on real screens; then documentation, contribution process, and a check against Stage 0's own success criteria.

Decisions so far

Stage 0 is an audit, but it already produces real architectural commitments. One primary button primitive replaces three near-identical buttons. A single app-wide focus indicator — not owned by any one component — has to clear 3:1 contrast on both a dark nav surface and white panels. Color uses two tiers: an internal reference ramp and role-based semantic aliases, with numbered brand steps the design spec defines.

Size and spacing scales stay internal to the system; feature teams only ever receive composite, role-based type styles through components such as Text, never raw scale values or public utility classes. Components are classified by layer before implementation — primitive, composed pattern, or product feature — so a status badge's visual states live in the system while the status-to-badge mapping stays product-owned.

Why it matters

Most of my design-system work has started from an existing platform already in production. This course starts from zero and makes every judgment call explicit: what becomes a token versus a component versus a product feature, who owns it, and what would change if a second, differently-branded product consumed the same system.

It is the same discipline behind Checklist Auditor and the Fabric UX DevKit — evidence before action, an explicit verdict, and a record a reviewer can actually check — applied to the earliest, least glamorous part of building a design system instead of to an existing one.

Current status

This is a private, local, in-progress learning project with no deployed build. It is currently in Stage 0 (Audit, identify layers, plan the system), on the task of writing design principles and success criteria. Eleven earlier Stage 0 tasks are complete and recorded in the decision log; no tokens or components have been implemented in code yet, which is intended at this point in the curriculum.
